Reverse-Engineering a Jane Street ASIC

Recovering a netlist from a raw GDS layout, solving for a 122-bit unlock key, and reading out the message underneath.

Jane Street's 2026 puzzle shipped as puzzle.gds — a raw silicon layout targeting the SkyWater sky130 process, with no schematic and no netlist. The task: figure out what the circuit does, find the input sequence that makes it succeed, and read whatever it says back. Below is the full pipeline, what went wrong along the way, and where an LLM fit into the process.

The pipeline

Four stages, each solving a different problem.

1. Extraction — two independent paths

I used Magic, in batch mode, to pull a hierarchical SPICE netlist directly out of puzzle.gds, against the sky130 sky130_fd_sc_hd PDK installed via volare. Standard-cell instances keep their library names in the GDS itself, so gate-type recognition came for free — no pattern-matching against a cell library was needed.

A single extraction is only as trustworthy as the tool that produced it, so I built a second one from scratch: a custom LVS deck in KLayout working directly on raw process layers (nwell, diff, poly, licon, li1, met1–5), with its own MOSFET recognition and no cell-library shortcut. Netgen compared the two, and all 7,932 devices matched down to the last transistor — the only residual difference was a cosmetic diode-merge artifact in inert ESD protection structures.

2. Analysis — what the gates compute

A netlist is just a graph of gates and wires; it doesn't say what it means. I wrote a parser for the sky130 Liberty (.lib) files to turn each cell name into its actual boolean function and, for flip-flops, its clock/next-state/clear/preset behavior — more robust than reading the behavioral Verilog, which leans on primitives older Yosys frontends can't parse.

Tracing the fan-in cone of success pulled in 483 of 722 gates and 79 of 84 flip-flops, plus the I input. Flip-flop inputs turned out to be combinational mixes of several signals, not straight pass-throughs — the signature of an LFSR/CRC-style mixer, not a plain shift-register-and-compare. Nothing is tied to a constant, so the comparison target isn't readable off the gates by hand; it's encoded structurally. That ruled out manual analysis and pointed at a solver.

The puzzle's own hint — that part of the design generates output but doesn't affect success, and needs separate simulation — matched exactly. That region sits outside the success cone entirely, built from flip-flops with no simple reset.

3. Solving — z3 over the unrolled circuit

I unrolled the circuit cycle-by-cycle into a boolean formula for z3 — one fresh variable per net per cycle, tied to its driving gate's function — and asked for an input sequence that forces success to 1. Free enable found a working but strange 289-cycle solution; pinning enable = 1 throughout — the natural way to run the chip — found a clean 122-cycle solution in about nine seconds.

I cross-checked it two ways: a separate plain-boolean forward simulator, with no SAT involved, re-evaluated the netlist concretely and agreed exactly. Re-solving with each bit individually flipped and blocked showed 121 of the 122 bits are essential — flipping any one makes success unreachable. Only the last bit is a genuine don't-care.

4. Reading the answer

success asserting doesn't hand you a message — it's a single flag, and the byte stream on O[7:0] is computed by a physically separate part of the chip. So the final simulator covers the union of both fan-in cones, and running the key through it streams fifteen bytes on O[7:0], one per cycle, starting the cycle success first goes high:

28 2a 20 54 57 4f 20 53 54 41 52 53 20 2a 29

As ASCII: (* TWO STARS *) — valid OCaml comment syntax. Nothing here was ever fabricated or displayed anywhere; a simulator stepped the netlist cycle by cycle and printed the value of eight logic nets each time. Grouping those bits into bytes and reading them as ASCII was my interpretation, not the chip's.

Two things corroborate the decode. Wrong keys decode cleanly through the identical simulator: an all-zero input gives EMPTY SKY, other wrong keys give TRY AGAIN. And the two GDS cells sitting inside the hint region, INTERNAL_7 and INTERNAL_3, turned out to contain exactly one bare rectangle each on an unrecognized marker layer — no transistors. They're a deliberate visual redaction in the published layout, not real logic; everything needed for O[7:0] was already in the recovered netlist.

Where an LLM fit in

I used Claude Code throughout as a pair-programmer for the pipeline itself — the Magic Tcl extraction script, the SPICE and Liberty parsers, the cone-analysis pass, and the z3 unrolling logic — then iterated against real failures instead of getting it right up front. The value wasn't "ask an AI to reverse-engineer a chip"; it was compressing the write-run-debug loop across a stack of unfamiliar tools (Magic's Tcl API, Liberty's quoting conventions, z3's Python bindings), while the actual reverse-engineering judgment — what to extract, what a suspicious cone shape implies, whether a solution is clean — stayed with me. Concretely, that meant validating every stage against the repo's trivial warmup circuit before trusting it on the real target, and several of the bugs below were caught by reading generated code line by line rather than trusting that it ran without errors.

What went wrong

Kept here because each one produced a plausible-looking wrong answer before it produced the right one.

  1. The wrong netgen. Ubuntu's apt install netgen pulls a 3D FEM mesh generator with the same name, not the VLSI LVS tool — had to remove it and build the real one from source.
  2. Liberty parsing, three ways. Cell/pin names in this PDK's .lib are quoted, not bare, so a naive regex returned empty dictionaries. function : "..."; needed a start-of-line anchor or it also matched power_down_function, silently substituting the wrong boolean expression for every gate. And constant-driver cells report their function as the bare literal "0"/"1", which an identifier-only tokenizer chokes on.
  3. Filtered out a real driver. The constant-value generator was caught by the same filter meant to strip physical-only decap/tap/fill cells, producing a "combinational loop?" error that was actually a missing driver.
  4. Dropped a second output pin. The constant-driver cell has two outputs, HI and LO. An early evaluator only kept the last output pin seen per instance — invisible until the wider output cone needed the dropped one.
  5. Not every flip-flop resets. The output-generator flip-flops have neither clear nor preset. Force-zeroing every flop at cycle 0 corrupted that region's state and produced garbled, non-ASCII output even with the correct key — fixed by simulating a couple of clock edges with reset asserted and letting each flop's real logic settle.
  6. Shell variables silently vanishing. Variables referenced inside a command bridged from the host shell into WSL got stripped before WSL ever saw them, which quietly redirected output to the wrong path mid-session. Fixed by writing real script files and invoking them by path instead of inlining variables.
